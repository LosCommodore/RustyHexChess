# RustyHexChess: WASM Frontend Integration Plan

## Context

The RustyHexChess Rust engine is feature-complete with move generation, special moves (en passant, promotion), check/checkmate detection, and a solid type-state architecture. Currently it only has console display. This plan outlines building a TypeScript frontend via WASM + localhost to provide an interactive hexagonal chess UI.

## High-Level Architecture

```
┌─────────────────────────────────────────────────────────┐
│         TypeScript Frontend (React/Vue/Vanilla)         │
│  - Hexagon board rendering (Canvas/SVG)                │
│  - Move UI (click to select/move)                       │
│  - Game state display                                   │
└────────────────┬──────────────────────────────────────┘
                 │ (JavaScript function calls)
┌────────────────▼──────────────────────────────────────┐
│         WASM Bridge (Generated by wasm-bindgen)        │
│  - Exported Rust Game API to JS                        │
│  - JSON serialization of board state                   │
└────────────────┬──────────────────────────────────────┘
                 │ (Native Rust execution)
┌────────────────▼──────────────────────────────────────┐
│   Rust Engine (hexagon_logic crate)                   │
│   - Game<NormalTurn|PromotePawn|GameOver>            │
│   - Move validation, legal move generation            │
│   - Board state, check/checkmate logic                │
└─────────────────────────────────────────────────────────┘
```

## Implementation Plan

### Phase 1: WASM Bindings for Rust Engine

**Goal**: Expose the Rust game API to JavaScript

**Steps**:

1. **Add WASM dependencies to `engine/Cargo.toml`** (already added)
   - `wasm-bindgen = "0.2"` - Bridge between Rust and JS
   - `wasm-bindgen-futures = "0.4"` - For async support (if needed)
   - `web-sys = "0.3"` - Browser APIs
   - `serde_json` (already present) - JSON serialization

2. **Create `engine/src/wasm.rs`** (~200-300 lines)
   - Public WASM entry point that re-exports the game API
   - Wrapper functions that convert between Rust types and JS-friendly types:
     - Game state as JSON: `fn get_game_state(game: &Game) -> String` → serialize board, current turn, king check status
     - Move result as JSON: `fn make_move(game_json: &str, origin: &str, dest: &str) -> Result<String, String>` → take game state, apply move, return updated state
     - Legal moves as JSON: `fn get_legal_moves(game_json: &str, position: &str) -> Result<String, String>`
     - Promotion: `fn promote(game_json: &str, piece_type: &str) -> Result<String, String>`
   - Create Rust wrapper types with `#[wasm_bindgen]` annotations for types that cross the boundary:
     - `WasmPosition` wrapping hexagonal coordinates
     - `WasmBoard` for serialized board state
   - Use `serde_json` to convert Game state to/from JSON strings for transport

3. **Configure `engine/Cargo.toml` for WASM** (already done)
   - Add `[lib]` to build as both cdylib and rlib
   - Configure for WASM: `crate-type = ["cdylib", "rlib"]`

4. **Test WASM layer locally**
   - Use `wasm-pack build --target web` to generate WASM module
   - Verify exported functions exist in generated `.d.ts` type definitions

**Critical files**: 
- `engine/src/wasm.rs` (new)
- `engine/Cargo.toml` (already updated with wasm-bindgen dependencies)

### Phase 3: Hexagonal Board Rendering

**Goal**: Render interactive hexagonal chess board with pieces

**Steps**:

1. **Create `frontend/src/components/Board.ts`** (~400-500 lines)
   - Use **Canvas 2D API** (simpler than WebGL) or **SVG** (more semantic)
   - Recommendation: **Canvas** for performance, but SVG for easier piece positioning
   - Hexagon geometry:
     - Flat-top hexagons (width > height, which fits your board layout)
     - Reference engine coordinates directly from `engine/src/coordinates.rs`
     - Calculate pixel positions from hex coordinates using axial math:
       ```
       x = hex_size * (3/2 * col)
       y = hex_size * (√3/2 * col + √3 * row)
       ```
   - Render grid, highlight selected piece, highlight legal moves as overlays
   - Mouse event handling: click hex → emit "selected" event with Position

2. **Create `frontend/src/components/UI.ts`** (~200-300 lines)
   - Display current turn, game status (normal/check/checkmate/promotion)
   - Promotion dialog: 4 radio buttons (Queen, Rook, Bishop, Knight)
   - Move history sidebar or log
   - Undo button (calls engine)
   - New game button

3. **Piece rendering**
   - Use Unicode chess symbols (♔ ♕ ♖ ♗ ♘ ♙ and their black variants ♚ ♛ ♜ ♝ ♞ ♟)
   - Or simple SVG paths for custom hexagon-chess piece glyphs
   - Color by side (white/black, or use the engine's existing color scheme)

**Critical files**:
- `frontend/src/components/Board.ts` (new)
- `frontend/src/components/UI.ts` (new)
- `frontend/src/styles/board.css` (new)

### Phase 4: Game State Management

**Goal**: Bridge WASM engine calls with UI updates

**Steps**:

1. **Create `frontend/src/wasm/engine.ts`** (~150-200 lines)
   - Import compiled WASM module: `import init, * as wasm from '../../engine/pkg'`
   - Wrapper class `GameEngine`:
     - `async load()` - initialize WASM
     - `newGame(board?: string): GameState` - call `wasm.new_game()`, return serialized state
     - `makeMove(game: GameState, origin: string, dest: string): GameState | Error`
     - `getLegalMoves(game: GameState, pos: string): string[]`
     - `promote(game: GameState, pieceType: string): GameState | Error`
     - Cache game state as JSON string to pass between JS ↔ WASM

2. **Create `frontend/src/components/Game.ts`** (~300-400 lines)
   - Main game loop/controller
   - Properties: `currentGameState: GameState`, `selectedPiece: Position | null`, `legalMoves: Position[]`
   - Methods:
     - `onHexClick(pos: Position)` - handle board clicks
       - If no piece selected: show legal moves for that position
       - If piece selected and pos is legal: call engine.makeMove(), update board
       - If promotion required: show dialog, wait for choice, call engine.promote()
     - `onPromote(pieceType: string)` - call engine.promote()
     - `onUndo()` - call engine.undo()
     - `onNewGame()` - reset state
   - Emit events to Board and UI components on state changes

3. **Create `frontend/src/index.ts`** (main bootstrap, ~100 lines)
   - Initialize engine, create Game controller, mount Board and UI
   - Event loop: wire up event handlers

**Critical files**:
- `frontend/src/wasm/engine.ts` (new)
- `frontend/src/components/Game.ts` (new)
- `frontend/src/index.ts` (new)

### Phase 6: Local Development & Testing

**Goal**: Verify end-to-end integration

**Steps**:

1. **Run development server**
   ```bash
   npm run dev
   ```

   - Vite dev server reloads browser on TS/CSS changes

2. **Manual testing checklist**
   - Create new game → board renders with all pieces in correct positions
   - Click piece → legal moves highlight
   - Click legal move → piece moves, board updates, turn switches
   - Verify capture logic works (click enemy piece square)
   - Trigger en passant → verify capture behavior
   - Reach promotion zone → promotion dialog appears
   - Select promotion piece → pawn converts, game continues
   - Trigger check → UI marks check state
   - Trigger checkmate → game ends with message
   - Undo move → board reverts, turn switches back

3. **Browser DevTools**
   - Check console for WASM initialization errors
   - Inspect network tab: verify `.wasm` file loaded
   - Use Profiler to measure rendering performance

## Technology Choices

| Component | Choice | Why |
|-----------|--------|-----|
| WASM | `wasm-bindgen` + `wasm-pack` | Standard, battle-tested, great TypeScript support |
| Frontend | Vanilla TypeScript (no framework) | Minimal dependencies, direct control, overkill for this single-page game |
| Rendering | Canvas 2D | Fast hexagon rendering, easier than SVG for grid |
| Build Tool | Vite | Fast rebuilds, excellent WASM support, simpler config than Webpack |
| State | In-memory JS objects | WASM serialization handles persistence if needed later |

## Notes

- **No networking**: WASM runs entirely in browser, no backend needed
- **Serialization**: Game state passed as JSON strings over WASM boundary (slight performance overhead, but negligible for turn-based game)
- **State persistence**: Can add `localStorage` save/load later if desired
- **Scaling**: If you later want network multiplayer, this architecture can layer a WebSocket server on top without changing the frontend much
